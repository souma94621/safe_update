# Безопасное обновление ПО — мок-реализация ГОСТ Р 72118 А.10

Мок-система для обновления ПО, реализующая требования ГОСТ Р 72118 Шаблон «Безопасное обновление» (А.10).

## Быстрый старт

Все команды выполняются из корня проекта.

### 1. Генерация ключей

```bash
python generate_cert.py
python generate_keys.py
```

Создаст:
- `keys/server.crt`, `keys/server.key` — TLS-сертификат и ключ сервера
- `keys/server_private.pem`, `keys/client_public.pem` — ключи для подписи/верификации пакетов

### 2. Запуск сервера обновлений

```bash
cd server
python main.py
```

Запустится на `https://localhost:8000`. Раздаёт пакеты из `packages/` и подписанные метаданные.

### 3. Запуск веб-интерфейса клиента

```bash
cd web
python app.py
```

Откройте `http://127.0.0.1:8001` в браузере.

### 4. Запуск тестов

```bash
python -m pytest tests/ -v
```

## Архитектура

Система состоит из компонентов, взаимодействующих через временное хранилище с контролем доступа:

<img width="622" height="581" alt="image_2026-10-08_12-09-06" src="https://github.com/user-attachments/assets/9e9d0706-5f09-4918-bfbe-5dd1f6a8d825" />


**Компоненты:**

- **Менеджер** — оркестрирует полный цикл обновления (шаги 1–9 из А.10.4)
- **Загрузчик** — скачивает пакет и метаданные через HTTPS с аутентификацией сервера (TLS)
- **Верификатор** — проверяет целостность (SHA-256), аутентичность (RSA-PSS), актуальность версии
- **Установщик** — записывает в основное хранилище (A/B-схема для отката), инициирует установку
- **Монитор** — контроль разграничения доступа между компонентами (не просто логгер)
- **Временное хранилище** — изолированное хранилище с конечным автоматом (WRITABLE → SEALED → VERIFIED)

## Соответствие ГОСТ Р 72118 А.10.4

| № | Требование | Реализация | Модуль |
|---|-----------|-----------|--------|
| 1 | Аутентификация сервера | TLS-сертификат, проверка в `loader.py` | `loader.py:22-26` |
| 2 | Откат обновления | A/B-схема в `data_storage.py`, переключение слотов | `installer.py:18`, `data_storage.py:53-63` |
| 3а | Проверка целостности | SHA-256 хеш пакета, сравнение в verifier | `verifier.py:45-46` |
| 3б | Проверка аутентичности | RSA-PSS подпись версии + хеша, проверка в verifier | `verifier.py:50-54`, `endpoint.py:15` |
| 3в | Проверка актуальности | Версия включена в подпись, не может быть подменена | `endpoint.py:15`, `verifier.py:50` |
| 4 | Разграничение доступа | Монитор контролирует доступ по состояниям (WRITABLE/SEALED/VERIFIED) | `monitor.py:10-19`, `views.py:7-11` |

## Состояния временного хранилища

Система работает в трёх состояниях конечного автомата:

<img width="570" height="570" alt="состояние хранилища" src="https://github.com/user-attachments/assets/0d2ce107-10c2-4035-ad48-ed9aae290700" />


1. **WRITABLE** — хранилище открыто для записи пакета загрузчиком
2. **SEALED** — хранилище закрыто, доступно только верификатору на чтение
3. **VERIFIED** — пакет прошёл все проверки, доступен установщику

Переходы:
- WRITABLE → SEALED: после `loader.download()`
- SEALED → VERIFIED: после `verifier.approve()`
- VERIFIED → WRITABLE: после `installer.install()` или `installer.rollback()`

## Ограничения мока

- **TLS**: проверяется закрепленный сертификат `server.crt`, но нет полной цепи сертификатов
- **Прямой доступ к хранилищу**: в коде возможна прямая запись в `DataStorage` без прохода через верификатор (обходит Монитор). В продакшене этого не будет благодаря изоляции процессов
- **Версия как строка**: сравнение лексикографическое при парсинге как `[int, int, int]`, но в отчёте версия хранится строкой
- **A/B откат**: поддерживается только один уровень отката (данные неактивного слота перезаписываются при следующей установке)

## Примечания по разработке

- Все компоненты — отдельные Python-модули
- Взаимодействие через JSON файлы (временное хранилище) и методы (Monitor, Views)
- Сервер и клиент коммуницируют через HTTPS (аутентификация сервера по TLS)
- Подпись рассчитывается на `версия + SHA256(пакет)`, а не на сам пакет
- Монитор реализует шаблон из ГОСТ и логирует каждый запрос доступа с вердиктом
